## 0. 基本理念（維持）

- 子どもを教材に合わせるのではなく、子どもの可能な動きに教材を合わせる。
- 入力方法の適性や本人の能力をアプリが断定しない。
- 操作回数の多さを主体性・意欲と同一視しない。
- 観測データと教員の解釈を分離する。
- 提案は参考情報であり、本人の実情に合わせて利用する注意書きを必須とする。
- （Phase 4統合で追加確認）cancelイベントは本人の失敗・能力不足・意図性を示すものと断定しない（4.4節）。
- **（DESIGN-V2-PERSISTENCE-1で追加確認）入力方式を跨いだcancel件数の合算・ランキング化は行わない（8章・9章）。**

## 1. 入力方式の設計

### 1.1 現状（コード現物で確認済み、Phase 3 checkpoint時点、変更なし）

- タッチ: `pointerdown`→`activate`、`pointermove`は直前記録位置から12px以上の移動時のみ`move`を記録（過剰発火防止が目的、スワイプ検出用の設計ではない）、`pointerup/pointercancel`→`release/cancel`。
- 外部スイッチ: スキャン方式のみ実装（`SCAN_SPEED_MS=1200`固定）。Space/Enter(非repeat)→`activate`、keyup→`release`。`move`は発火しない。blur等での強制解除時のみ`cancel`。
- 共通イベントschema: `{type, inputMethod, timestamp, duration, position, movement}`（Phase 3のまま、変更しない）。

### 1.2 スワイプは独立した入力方式とする（承認方針8、確定）

タッチモード中の`move`イベント有無を事後的に「スワイプを行った」と再解釈しない。スワイプは入力方式選択画面で教員が明示的に選ぶ**独立した入力方式**（`inputMethod: 'swipe'`、`VALID_INPUT_METHODS`への追加のみ）として実装する。

**しきい値の扱い（確定）**: 既存の12px（Access自身のmoveスロットリング用）・8px（`sawatte-hirogaru-app.html`のSWIPE_THRESHOLD_PX）のいずれも、**検証済みの推奨値として扱わない**。どちらも次の理由で転用できない。
- 12px: 目的がスワイプ検出ではなく、イベント発火量の抑制。
- 8px: 別アプリ（さわってひろがる）の画面・UI配置・対象利用者を前提にした値であり、Donomana Accessの対象利用者（重度・重複障害を含む）に対する検証は行われていない。

**【DESIGN-V2-PERSISTENCE-1で確定】Phase 5A実装時の暫定初期値は `10px` とする。** これは12px・8pxいずれの既存値とも異なる値であり、転用ではなく新規の仮置きである。コード上には「検証済みの推奨値ではなく、実機調整を前提とした暫定値である」ことを明記するコメントを残す。**しきい値を教員が調整するUIは、Phase 5Aの実装対象に含めない**（別途将来Phaseで検討する）。Phase 5Aでは定数としての仮置きのみを実装する。

### 1.3 タッチ中に観測された「動き」の扱い

タッチモードで記録された`move`イベントの有無は、以下のいずれであるかを区別できない客観的事実である（意図的なスワイプ／不随意な動き／教員の身体介助中の接触移動／タップの滑り、のいずれかは判別不能）。結果画面には「スワイプを行った件数」という解釈的な見出しを付けず、「接触中に動きが観測されたセッション数（意図性は判別できません）」として層1（3章）に表示する。

### 4.4 R3の表示方針（将来Phase実装時の指針として維持）

**【DESIGN-V2-PERSISTENCE-1で確定】R3（cancel比率による自動提案）は、Phase 6を含む初期実装の対象外とし、将来の別Phaseで検討する。** 以下の内容は、その将来Phaseで実装する際の設計指針として維持する（本文書では確定仕様ではなく、実装の前提とすべき考え方を記す）。

cancel（操作が完了しなかった）は、本人の失敗・能力不足・意図性を示すものと**断定しない**。理由:
- タッチの`cancel`（`pointercancel`）は、ブラウザ側のジェスチャー競合・マルチタッチ干渉等、**子どもの操作とは無関係な技術的要因でも発生する**。
- 外部スイッチの`cancel`は、現在の実装では**フォーカス離脱（blur）時の強制解除**でのみ発生する（押下中にタブ・アプリが切り替わった等）。これも子どもの操作能力とは直接関係しない事象である。

したがってR3を将来実装する場合も、表示文言は原因を特定・断定する表現を避け、**入力環境や操作方法の確認を促す控えめな提案に限定する**。

> （将来Phaseでの文案例）「○○方式では、操作が完了しなかった(cancel)割合が高く観測されました。周辺機器の設置や操作のしやすさを確認してみてください。原因がお子さま自身にあるとは限りません。」

### 4.5 R3の最小観測件数・分母分子の定義（承認方針5、未確定事項・将来Phaseへの前提条件）

本統合作業にあたり、前Phase設計文書・改訂文書の両方のR3に関する記述を再確認した。結果:

- **cancel比率の分母の定義（例: `cancel/(activate)`か`cancel/(cancel+release)`か等）は、いずれの既存文書にも記載がない。**
- **R3を評価するために必要な最小観測件数（例: cancel+release合計が何件以上あれば比率として意味を持つか）も、いずれの既存文書にも記載がない。**

**本文書ではこれらを推測で確定しない。** **【DESIGN-V2-PERSISTENCE-1で確定】R3自体が初期実装（Phase 6）の対象外となったため、本項の3点は「Phase 6着手前に解消すべき事項」ではなく、「R3を実装する将来の別Phenの着手前に解消すべき事項」として位置づけを改める。**

1. 分母の定義（cancel/(cancel+release)が最も自然な候補だが、確定ではない）。
2. 最小観測件数（分母が小さい場合、わずか1〜2件のcancelで50%を超えてしまい、R3が過剰発火するリスクがある。C1の「セッション数2件以上」とは別に、**イベント単位での最小件数**を定める必要がある）。
3. 50%という閾値自体の妥当性（既存文書がそのまま引用した値であり、Donomana Accessの実データでの検証は行われていない）。

## 8. 教育的リスクと対策（前Phase設計文書を維持・R3関連・cancel合算禁止を追加）

1. 数値の一人歩き → 注意書き常時表示、数値の並び順を中立に保つ。
2. 少数データでの過信 → C1〜C4の厳格な運用。
3. 教員メモの個人情報化 → 選択式を既定とし自由記述を採用しない（5章）。
4. 設定差の見落とし → C3による機械的検出。
5. 「アセスメント」という名称の重さ → UI名称は「振り返り」等、診断的でない表現を別途検討。
6. （Phase 4統合で追加）R3のcancel比率が、技術的要因（ブラウザのジェスチャー競合、フォーカス離脱）による結果を子どもの能力の問題と誤読されるリスク → 4.4節の文言限定、4.5節の未確定事項の解消を実装前に必須とする。R3自体は初期実装の対象外（4.3節）。
7. **【DESIGN-V2-PERSISTENCE-1で追加】入力方式間でcancel件数を単純合算し、「どの入力方式が優れているか」のような適性評価・ランキングに使う誤用のリスク** → cancel件数は常に入力方式別に保持し（2章の表のとおり）、Phase 6で新設する集計関数は入力方式を跨いだcancel合計値・ランキングを生成・公開しない（9章）。
