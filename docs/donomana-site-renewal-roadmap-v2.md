## 4. 今後、他ページに共通化すべき部分（優先順）

1. **アクセシビリティ関連の共通化（最優先）**：共通A11y Widget化・スイッチスキャン共通化・PINロック共通化・ハイコントラスト統一。アクセシビリティ全体監査で「29アプリの実装がバラバラ」「共通パネル内部のボタンが到達不可」という事実が判明しており、他の共通化より先に着手する（詳細は6.1節）。
2. **共通CSSファイルへの切り出し**：63以上のページが同じフォント読み込み・配色トークンをコピペしている。`assets/css/base.css`のような1ファイルに切り出し`<link>`で読み込む形にすれば、以後の配色変更が1箇所で完結する。ビルドツール不要（静的`<link>`で足りる）。
3. **共通ヘッダー/フッターの部品化**：完全なテンプレートインクルードの仕組みは無いが、`generate.js`を拡張して「ヘッダー/フッターHTML断片」を各ページに注入する運用にすれば、ナビ変更が全ページへ機械的に波及できる。
4. **ロゴSVGの外部ファイル化**：現状ページごとに同一SVGコードを複製。`<img src="/symbol.svg">`化すればコード量・保守性が改善する（ただしインラインSVGは色の動的変更ができる利点があるため、要件次第で判断）。
5. **新トークン名をphilosophy.html/about.htmlにも反映**：値自体はほぼ同じなので、トークン名（`--line` `--shadow-soft`等）を揃えるだけの低リスク作業。
6. **学習アプリ群のフォント方針の検討**：現状`Noto Sans JP`中心。ブランドの雰囲気を出すため見出し部分だけ"M PLUS Rounded 1c"を使う等の部分適用も選択肢。ただしアプリ本体は可読性・操作性が最優先のため、無理な統一はしない判断もありうる。

## 5. 変更すると既存機能に影響する可能性がある部分

- **`generate.js` / `apps-data.json` / `dynamic-card-css` / `card-<slug>`命名規則**：`index.html`内の個別アプリ配色はビルド時自動生成される領域。ここを手動で変更すると、次回`generate.js`実行時に上書きされる、または命名規則の不整合で表示が崩れる可能性がある。
- **各学習アプリの`localStorage`/`IndexedDB`キー**：学習記録の保存に使用（ひらがな等）。ファイル名やパスを変更すると、既存の保存データ・ブックマーク・共有済みURLが失われる恐れがある。
- **孤立ファイルの削除判断**：ルート直下の`*-detail.html`重複29件、および孤立学習アプリ5件は、内部からは参照されていないが、外部サイトやSNS等から直接リンクされている可能性はゼロではない。削除前にアクセス解析等で実アクセスの有無を確認するのが安全。
- **`.github/workflows/generate.yml`**：`main`へのpushのたびに`node generate.js`を自動実行しコミットする。共通CSS化等で`generate.js`の生成ロジックそのものを変更する場合、このワークフローへの影響を要確認。
- **学習アプリ内のJS連動クラス名**：音声読み上げ・スイッチスキャン・視線入力対応など、`index.html`の`a11y`機構と同様に特定のクラス名/idにJSが強く依存しているパターンが他ページにもある可能性が高い。共通化の際はクラス名・idを維持することが必須。
- **スイッチスキャンの実装方式が29アプリでバラバラ**（最低8方式に分類、アクセシビリティ全体監査で判明）：共通化の際、実フォーカスを使うスキャン方式（hiragana-learn/katakana-app/suji-manabou/tokei-app等）は、共通パネル側がフォーカス移動を実装すると競合しうる。個別アプリごとの現状把握なしに一括置換すると回帰の恐れがある。

## 6. 改修優先度

優先順位は次の6段階とする：**アクセシビリティ → 共通コンポーネント → UI統一 → パフォーマンス → 新機能 → プラットフォーム化**。
Ver.1.0時点の優先度A/B/C（Design System Ver.2.0 §10に記録済み）は、以下の6段階に統合・更新した。

### 6.1 アクセシビリティ（最優先）
- 共通A11y Widget化（29アプリ共通の設定パネル基盤設計。独立フェーズとして扱う）
- スイッチスキャン共通化（8方式の分裂解消。共通パネル起動ボタンの到達性、パネル内部ボタンの到達性を含む）
- PINロック共通化
- ハイコントラスト統一

### 6.2 共通コンポーネント（旧優先度A中心）
- 共通CSSファイルへの切り出し（フォント読み込み・配色トークンの一元化）
- `philosophy.html` / `about.html` への新トークン名の反映（値はほぼ同一のため低リスク）
- 孤立ファイル（重複detailページ29件・孤立学習アプリ5件）の実アクセス調査 → 削除 or 現状維持の判断

### 6.3 UI統一（旧優先度B/C）
- `app-intro.html` / `wizard.html` / `switch-gaze-guide.html` / `terms.html` / `home-screen-guide.html` / `404.html` への新デザイン適用（index.htmlと同じ「ヘッダー→ヒーロー→ボタン→カード→フッター」の型を横展開）
- 共通ヘッダー/フッターの部品化（`generate.js`拡張によるHTML断片注入）
- 個別学習アプリ29本のUIデザイン統一（操作性・可読性優先のため慎重な検討が必要。フォント統一の是非を含む）
- ロゴ等SVGの外部ファイル化・アイコンの共通コンポーネント化

### 6.4 パフォーマンス改善
- 共通コンポーネント化・UI統一の完了後に着手する。個別施策はその時点のサイト構成に合わせて具体化する。

### 6.5 新機能
- 教員向け機能追加。要件は着手時に具体化する。

### 6.6 プラットフォーム化
- 6.1〜6.5の完了を前提とする長期方針。個別施策は着手時に具体化する。

## 7. 次に修正するページの提案

### 提案：`app-intro.html`

**理由**
- `index.html`の「アプリ紹介ページ」バナーから直接遷移する、トップページに次ぐ主要な導線
- ブランドフォント（Rounded Mplus 1c）は既に読み込み・適用済みだが、配色トークン（`--ink` `--line` `--shadow-soft`等）と共通ヘッダー（`site-header` / `header-inner`）はindex.html刷新前のままで、Design System Ver.2.0の規約が未適用
- 2279行と規模が大きく、アプリ一覧的な構造を持つと推測されるため、`index.html`で確立した「ヘッダー／カード／セクション」パターンをそのまま横展開しやすい
- ユーザーが指定した「アプリ一覧、紹介ページ」カテゴリの代表であり、次の一手として費用対効果が高い

次のステップとしては、`index.html`刷新時と同様に**現状確認→デザイン案（Before/After）の提示→承認後に段階的実装**の流れで進めることを想定。

なお、この提案はDesign System Ver.2.0 §10.4「次の一手」にも同一内容が引き継がれている（出典として本書を参照）。
