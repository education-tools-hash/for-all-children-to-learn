## 0. 基本理念（v2.0から継承、変更なし）

- 子どもを教材に合わせるのではなく、子どもの可能な動きに教材を合わせる。
- 入力方法の適性や本人の能力をアプリが断定しない。
- 操作回数の多さを主体性・意欲と同一視しない。
- 観測データと教員の解釈を分離する。
- 提案は参考情報であり、本人の実情に合わせて利用する注意書きを必須とする。
- 自力操作を支援付き操作より優れていると評価しない。身体的支援がある活動も尊重する。
- 観察記録を入力方式の自動ランキング・能力評価・主体性判定に使用しない。

## 1. 既存データ構造（Phase 5A checkpoint現物確認結果、変更なし）

- `donomana_access_log_v1`: `{schemaVersion:1, sessionId, inputMethod, startedAt, endedAt, events[]}`。`inputMethod`は`'touch'/'switch'/'keyboard'/'swipe'`。
- `sessionId`は`makeSessionId()`で生成（`'access-' + Date.now().toString(36) + '-' + Math.random().toString(36).slice(2,8)`）。暗号学的一意性は要求しない。`state.sessionId`は`startActivity()`で生成され、次の`startActivity()`まで保持される（終了画面遷移後も保持される）。
- `clearSessions()`は**キー全体を削除**する。個別セッション単位の削除機能は現状存在しない。
- `appendSession()`は`MAX_SESSIONS=200`を超えると古いものから切り捨てるが、**どのsessionIdが切り捨てられたかを自身は呼び出し元に返さない**。呼び出し側（HTML）がトリム前後の差分から判定する必要がある。
- `renderStoredSummary()`は**全セッションの合計件数・合計activate数のみ**を表示する一文であり、個別セッションを一覧表示する画面は存在しない。
- `onSwitchKeyDown()`/`onSwitchKeyUp()`は`state.inputMethod !== 'switch'`のみを判定し、**現在どの画面がactiveかを確認していない**（後述7章で詳述）。

## 3. 観察項目の最終Draft（4項目）

### A. 活動時の姿勢

```
posture: "未記録" | "座位" | "立位" | "臥位" | "その他"
```

- v2.0の「側臥位」は「臥位」へ広域化（側臥位・仰臥位等を包含する上位概念として扱う）。
- v2.0の「抱かれている」は本案では独立選択肢として残さない。**姿勢（身体の構え）と支え方（誰に・何に支えられているか）は別の概念であることを明記する**（抱っこは「支え方」の一種であり、「立位で抱かれている」「座位で抱かれている」等、姿勢とは独立に組み合わさり得るため、単一の姿勢選択肢に押し込めると情報が失われる）。
- **推奨**: 「その他」を選んだ場合のUI表示に「（抱かれている場合など）」という補足テキストを添える。
- **分類上の限界（明記）**: この補足は「抱かれている」を姿勢として正式に分類するものではなく、**該当する記録先が無いために「その他」を使うことを示すヒントに過ぎません**。将来、支え方（抱っこ・車椅子等）を独立した軸として追加する場合は、別フィールド化が必要であり、本v1では見送ります。
- **姿勢と補助具の区別（監査指摘④、明記）**: 活動時の姿勢は身体の構え（座位・立位・臥位等）を記録する項目であり、車椅子・バギー・座位保持装置などの補助具・機器の使用有無とは別の概念である。本初期版では補助具・機器の使用情報は記録対象としない。上記の「抱かれている」の扱い（その他＋表示補足）もこの区別を前提とし、支え方・補助具を姿勢の選択肢に混同して追加するものではない。

### B. 活動時の支援（複数選択、3状態構造）

```
support: { recorded: boolean, types: string[] }
```

- `types`の許容値: `"声かけ・音声による促し" | "視覚的な提示・促し" | "身体的な支援" | "姿勢・機器配置などの環境調整"`
- **3状態の厳密な区別**:
  1. **未記録**: `{ recorded: false, types: [] }`（このセクションを教員が一切操作しなかった状態）
  2. **支援・環境調整は特になし（確認済み）**: `{ recorded: true, types: [] }`（教員が確認のうえ「特に支援は無かった」と明示的に記録した状態）
  3. **具体的な支援・環境調整あり**: `{ recorded: true, types: [1件以上] }`
- **UI上の排他制御**: 「未記録」は独立したトグル（ラジオボタン的な単一選択、既定でON）として表示し、「支援・環境調整は特になしを確認した」ボタンまたはチェックボックスと、4種別のチェックボックス群は、「未記録」がOFFになった時のみ操作可能にする。4種別のいずれか1つでもチェックされた場合、「支援・環境調整は特になし」は自動的に解除される（矛盾する同時選択を防止）。

### D. 教員が観察した活動への関わり（複数選択、整合性ルールあり）

```
teacherImpression: { recorded: boolean, observations: string[] }
```

- `observations`の許容値: `"自分から働きかける様子が見られた" | "促しをきっかけに働きかける様子が見られた" | "判断が難しい"`
- **「判断が難しい」と具体的観察の同時選択可否（検討結果）**: 「判断が難しい」は「見分けられなかった／確信が持てなかった」という教員の不確実性の表明であり、同じ1回の観察の中で「自分から働きかける様子が見られた」という確信的な観察と論理的に両立しません。**したがって「判断が難しい」は`observations`内で他の2項目と排他とする**ことを推奨します。一方、「自分から働きかける様子が見られた」と「促しをきっかけに働きかける様子が見られた」は、同一活動内で場面により両方が見られることが現実にあり得るため、**この2つの間は複数選択を許容**します。
  - UIの排他制御: 「判断が難しい」をチェックすると他の2項目が自動解除され、逆に他の2項目のいずれかをチェックすると「判断が難しい」が自動解除される。
- **未記録との区別**: `recorded=false`（未記録、セクション未操作）と`recorded=true, observations=[]`は本項目では区別する必要がない（具体的観察が0件なら実質「未記録」と同義であるため）。ただし構造の一貫性のため、B項目と同じ`{recorded, types/observations}`形式で統一する。
- **序列化回避の明記**: 「自分から働きかける」「促しをきっかけに」の2選択肢は**優劣を示すものではなく、どちらも等しく有効な活動参加のかたち**であることをUI上の注記で常時明示する（後述7章）。本項目は観察・解釈情報であり、能力評価・主体性判定・入力方式のランキングには使用しません。

### C. 主な操作部位

```
operationPart: "未記録" | "手・指" | "頭部・顔" | "足" | "その他" | "該当なし"
```

- v2.0の`switchOperationPart`（スイッチ専用、右手/左手/頭部/足/その他/該当なし(スイッチ未使用)/未記録）を、**全入力方式（タッチ・スワイプ・外部スイッチ）に適用できるよう一般化**する。右手/左手は「手・指」に統合（左右の記録は本v1では扱わない）。
- **「その他」と「該当なし」は別の意味として扱う**: 「その他」＝観察した部位があるが選択肢に無い、「該当なし」＝この項目自体が今回の活動に意味を持たない（将来的なケースを想定した保留枠）。

## 4. 保存設計

```json
{
  "schemaVersion": 1,
  "sessionId": "donomana_access_log_v1の対応するsessionIdへの参照（外部キー、埋め込みではない）",
  "posture": "未記録",
  "support": { "recorded": false, "types": [] },
  "operationPart": "未記録",
  "teacherImpression": { "recorded": false, "observations": [] },
  "recordedAt": "2026-10-18T00:00:00.000Z"
}
```

- storageキー（新設）: `donomana_access_teacher_notes_v1`。既存の`donomana_access_log_v1`とは完全分離。
- 各フィールドはホワイトリスト検証（既存`makeEvent()`の`VALID_TYPES`検証と同方式）。
- **明示的な保存操作のみ**で書き込む。保存ボタンを押さずに画面を離れた場合、何も書き込まない。
- 全フィールドが初期状態（`posture`="未記録"、`support.recorded`=false、`operationPart`="未記録"、`teacherImpression.recorded`=false）のまま保存ボタンが押された場合も、**実質的な内容が無いためnotesキーには追加しない**（空レコードを作らない）。
- **upsert**: 配列内を`sessionId`で検索し、存在すれば置換、存在しなければ追加する。**ただし、既存レコードが存在する場合の置換には§4.2の安全確認が適用される**（無条件の置換ではない）。
- **保存済みsessionIdの存在確認**: 保存前に、現在の`donomana_access_log_v1`（正常に読み込めた場合のみ）にそのsessionIdが実在するか確認する。実在しない場合は保存を拒否する。
- 氏名・診断名・健康情報・自由記述欄は一切設けない。外部送信は行わない（localStorageのみ）。
- 既存の`donomana_access_log_v1`のschema・既存関数（`buildSessionRecord`/`appendSession`/`writeSessions`/`clearSessions`/`summarizeSessions`等）は一切変更しない。

### 4.1 `support`・`teacherImpression`のクロスフィールド整合性検証（監査指摘①）

UI上の排他制御（§3-B・§3-D）だけに依存せず、**保存時にデータ層でも以下を検証し、違反するレコードは保存を拒否する**。

**`support`**:
- `support.recorded`は`boolean`であること。
- `support.types`は、許容値（§3-Bの4種別）のみからなる配列であること。許容値以外の文字列・型不正（文字列でない要素）を含む場合は拒否する。
- `support.recorded === false`の場合、`support.types`は**必ず空配列**であること（`recorded=false`かつ`types`が非空、という組み合わせは矛盾として拒否する）。
- `support.recorded === true`かつ`support.types === []`は「支援・環境調整は特になし確認済み」を意味する。
- `support.recorded === true`かつ`support.types`が非空は「具体的な支援・環境調整あり」を意味する。
- `support.types`配列内に**重複する値を禁止**する（同一値が2回以上出現する場合は拒否する）。

**`teacherImpression`**（同等の検証を適用）:
- `teacherImpression.recorded`は`boolean`であること。
- `teacherImpression.observations`は、許容値（§3-Dの3項目）のみからなる配列であること。
- `teacherImpression.recorded === false`の場合、`teacherImpression.observations`は**必ず空配列**であること。
- `teacherImpression.recorded === true`の場合、`teacherImpression.observations`は有効な選択値を1件以上持つこと（未記録と判断困難を区別する。「未記録」は`recorded=false`、「判断が難しい」は`recorded=true, observations:["判断が難しい"]`であり、両者を同一視しない）。
- `teacherImpression.observations`配列内に**重複する値を禁止**する。
- **「判断が難しい」は、他の2項目（「自分から働きかける様子が見られた」「促しをきっかけに働きかける様子が見られた」）との同時選択を禁止する**（§3-Dの排他ルールをデータ層でも検証し、`observations`に「判断が難しい」と他の項目が同時に含まれるレコードは保存時に拒否する）。

上記のいずれかに違反する組み合わせ（許容値以外、型不正、矛盾する組み合わせ）は、UI側の排他制御の実装如何にかかわらず、**保存処理自体が拒否する**ことを設計要件とする。

### 4.2 既存レコードの保護（upsert時の安全確認、安全条件②）

保存（upsert）時、同一`sessionId`の既存noteが既に`donomana_access_teacher_notes_v1`内に存在する場合、**その既存レコードを§5-10の検証基準で検証してから置換の可否を決める**（無条件の置換は行わない）。

- **既存レコードが正常**（§5-10の検証をすべて満たす）な場合のみ、通常のupsert（新しい入力内容で置換）を許可する。
- **既存レコードが不正**（型不正・許容値外・§4.1のクロスフィールド制約違反）な場合、**無断で上書きしない**。今回の保存処理を保留し、理由を利用者に伝える（例:「以前の記録に問題が見つかったため、今回の保存を一時的に見合わせました。」等、断定的すぎない表現とする。原因の技術的詳細を利用者に強制的に開示する必要はないが、保存されなかった事実は伝える）。
- **既存レコードの`schemaVersion`が本文書の定義する値（`1`）と異なる**場合も、同様に**上書きしない**。将来のschema移行（`schemaVersion`を上げる場合の既存レコードの移行方法）は本文書では扱わず、別Phaseで設計する。
- 既存レコードの`sessionId`自体が欠落・型不正で安全に解釈できない場合も、安全側に倒して**上書き対象として扱わない**。新しい保存は、当該`sessionId`に対応する既存レコードが「存在しない」ものとして追加してはならない（既存の不正レコードを残したまま、別の正常レコードが重複して追加される事態を避けるため）。
- 上記のいずれで保留する場合でも、**不正レコードを無視して配列全体を書き戻すことはしない**。他の正常なレコードを巻き込んで消去・変更しない。

本節は§4.1（新規保存時のクロスフィールド検証）と組み合わさり、保存・upsertの経路全体で「正しい形式のレコードしか書き込まれない」ことを保証する。

## 5. 削除と整合性

1. **全件削除時**: `donomana_access_teacher_notes_v1`を**先に**削除し、成功を確認した後に`donomana_access_log_v1`を削除する（既存の`clearSessions()`自体は変更せず、呼び出し側で両キーの削除を順に実行する合成関数を新設）。
   - 理由: 中断時に最悪のケースが「notesは消えたがログが残る」（観察記録が孤立しない、安全側）になるようにするため。逆順だと中断時にログが先に消えてnotesが孤立する可能性がある。
2. **片方の削除失敗を成功として扱わない**: ログ側・notes側の削除結果（`{ok,reason}`）を両方確認し、いずれか一方でも失敗した場合は「削除しました」と表示しない。
3. **部分削除時の正確な通知**: 失敗した対象（ログ側／notes側のいずれか、または両方）を名指しする通知文に変える。
4. **MAX_SESSIONS=200超過時の孤立観察記録の整理**: `appendSession()`自体は変更せず、HTML側でトリム前後のsessionId集合を比較し、消えたsessionIdに対応する観察記録を新設の`pruneOrphanNotes(validSessionIds, notes)`（純粋関数）で除去する。
5. **正常読込時のみprune**: `safeReadSessions()`（既存、ログ側）・新設の`safeReadNotes()`（notes側）の**両方**の戻り値`anomaly`が`null`である場合のみ、prune処理を実行する。
6. **malformed JSON、read-exception時は自動削除しない**: ログ側が異常（`anomaly !== null`）の場合、実際のセッション状況が不明であるため、prune処理を今回のサイクルではスキップする。「異常＝ログが空」と誤認して観察記録を全削除することは明示的に禁止する。
7. **notes側の読込異常時も自動削除しない**: notes側が異常な場合も同様にprune処理をスキップする（notes自体をどう扱うべきか判断できないため、上書き・削除のいずれも行わない）。
8. **prune失敗時の通知と再試行（安全条件①、確定方針）**: prune処理の書き込み（notesキーへの`setItem`）が失敗した場合、既存の`classifySaveError()`で理由を分類し、**利用者が認識できる控えめな通知を表示する**（既存の保存失敗バナーと同様のパターン。詳細は下記）。
   - 通知は活動操作・観察フォームの入力を妨げない（モーダル等で操作をブロックしない）。
   - 失敗を成功と表示しない。
   - **既存データを削除・初期化して「修復」しない**（prune失敗時は`setItem`自体が行われないため、storage上の既存内容は変更されていない。localStorageの`setItem`は1キーに対して全体が成功するか例外を投げるかのいずれかであり、部分的な書き込みは発生しないため、失敗時に既存の保存済み内容がそのまま残っていることは設計上保証される）。
   - 再試行は、安全な条件（§5-5「ログ側・notes側とも正常読込時のみ」、かつ§5-11の複数タブ競合が疑われない場合）を満たす場合にのみ、次回の記録表示タイミングで行う。
   - **同一画面表示中に無制限な自動再試行を繰り返さない**（1回の画面表示につきprune試行は1回に限る）。
   - localStorageの読込異常や複数タブ競合が疑われる場合は、再試行そのものを保留する。
   - 通知文言は利用者が理解できる日本語とする。文言例（確定ではなく例示）: 「記録の整理を完了できませんでした。保存済みの記録はそのまま保持されています。」この「保持されています」は、上記のとおり`setItem`の性質上失敗時に既存データへの書き込みが発生しないことを根拠に述べてよい。これが保証できない失敗経路（将来、本節の前提が変わる場合）では、「保持しています」と断定せず「記録の整理を完了できませんでした。」のみを伝える。
9. **既存ログを観察記録の不具合によって変更・削除しない**: 観察記録側の保存・削除・prune処理は、`donomana_access_log_v1`に対して**読み取り専用**でのみアクセスする（sessionId存在確認・prune対象の算出のため）。書き込み・削除は一切行わない。

**原子的トランザクションが無いことの明記**: `donomana_access_log_v1`と`donomana_access_teacher_notes_v1`は別々のlocalStorageキーであり、ブラウザのlocalStorageには複数キーをまとめて更新するトランザクション機構がありません。したがって本設計は「厳密な原子性」ではなく、**「異常時は変更を保留し、次回の正常な読込時に整合性を再検証して穏やかに修復する」eventually-consistentな自己修復方式**を採用します。データを失う可能性がある性急な自動修復（異常時の一括削除等）は行いません。

### 5-10. 読込時のレコード単位検証（監査指摘②）

配列全体のJSON構造（malformed JSON / non-array）の検証（§5冒頭）に加えて、**配列が正常に構造解析できた場合でも、個々のnoteレコードについて以下を検証する**。

検証対象: `schemaVersion` / `sessionId` / `posture` / `support` / `operationPart` / `teacherImpression` / `recordedAt`。検証内容: 各フィールドの型、許容値（§3・§4.1のホワイトリスト）、配列内重複、§4.1のクロスフィールド制約。

- **不正レコードが1件でもあっても、アプリ全体をクラッシュさせない**。
- **不正レコードを検出しても、正常な他レコードを巻き込んで削除しない**（配列全体の上書き・全削除を行わない）。
- **不正レコードを単純に「存在しないもの」とみなして自動pruneの対象にしたり、配列全体を書き直したりしない**。不正レコードは「読めるが正しくない」状態であり、「存在しない」状態（§5の6・7の`anomaly`）とは異なる扱いとする。
- **安全な表示・隔離・書込保留方針**: 不正レコードは該当`sessionId`の観察記録を**表示しない（未記録として扱う）**が、storage上の生データからは削除しない。当該レコードに対する新たなupsert書き込みは、正しい形式で上書きされる限り許可する（教員が改めて保存すれば正常化される）。それ以外の自動的な書き換え・削除は行わない。
- **未知の`schemaVersion`の保全**: `schemaVersion`が本文書の定義する値（`1`）と異なるレコードは、**無断で変換・削除せず、将来の互換性のためそのまま保全する**（読込表示の対象からは除外するが、storageからは削除しない）。

### 5-11. 複数タブ・複数ウィンドウ利用時の制限（監査指摘③）

localStorageは、同一オリジンの複数タブ・複数ウィンドウ間で**原子的なread-modify-writeを保証しない**（最後に書き込んだ側がそれ以前の内容を無条件に上書きするlast-write-winsの挙動になる）。本設計は**単一タブでの利用を基本とする**が、以下のリスクと対応方針を明示する。

- **last-write-winsのリスク**: 2つのタブで本アプリを開いた場合、一方のタブでの観察記録の保存・upsertと、もう一方のタブでのprune処理（§5-4）が入れ違うと、片方の書き込みが古いスナップショットに基づく内容で他方の変更を上書きし、結果的にデータが失われる可能性がある。
- **古いスナップショットによる上書きの危険**: prune処理・全件削除処理のいずれも「読込→計算→書込」の手順を踏むため、読込から書込までの間に別タブが同じキーを更新すると、その更新が書込時に失われる。
- **自動pruneを実行する条件の明確化**: 自動prune（§5-4〜5-5）は、**その場で読み込んだログ・notesの内容のみを根拠に、その場で一度だけ計算・書込を行う**（長時間のタイマーやバックグラウンド処理としては実行しない）。これにより、prune自体が持つ読込〜書込の時間窓を可能な限り短く保つ。
- **競合が疑われる場合の自動削除・自動上書きの保留**: 本設計は、複数タブの競合を検知する機構そのものは実装しない（本Phaseでは複数タブ同期機能を新規実装しない。下記「storageイベント等の将来検討の位置付け」参照）。そのため「競合を検知して保留する」ことは保証できないが、§5-6・5-7の「異常時は自動削除しない」方針と同じ精神で、**疑わしい場合（例: 直前の読込結果と現在のstorage内容が一致しないことが判明した場合）は、自動削除・自動上書きよりも変更の保留を優先する**という一般原則を維持する。
- **利用者への通知**: 複数タブ競合そのものを検知して能動的に通知する機能は本v1では持たない。保存・削除操作自体の成功・失敗は既存の通知パターン（§5-2・5-3・6章）でその都度利用者に伝える。
- **storageイベント等の将来検討の位置付け**: ブラウザの`storage`イベントを監視すれば、他タブでの変更を検知できる場合があるが、**`storage`イベントだけでは完全な排他制御（相互排他ロック）を実現できるとは断定しない**（イベントは変更の事後通知であり、read-modify-writeの間の競合そのものを防止するものではない）。複数タブ対応が必要になった場合は、別Phaseで排他制御の方式（例: 書込前の再読込・比較による楽観的ロック等）を別途設計する。**本Phaseでは複数タブ同期機能を新規実装しない。**

### 5-12. prune判定基準の二軸性（安全条件のまとめ、監査フォローアップ）

prune（孤立観察記録の整理）に関わる判定は、**独立した2つの軸**で構成されることをここで明確にする。

- **軸A（sessionIdの対応関係）**: そのnoteレコードの`sessionId`が、現在の`donomana_access_log_v1`に存在するセッションに対応しているか（孤立／対応ありの判定、§5-4）。
- **軸B（レコード自体の妥当性）**: そのnoteレコードが、現在のschemaとして型・許容値・§4.1のクロスフィールド制約を満たしているか（§5-10の検証）。

**軸Bが不正であることだけを理由に、prune（削除）してはならない**。pruneは軸Aのみを基準に行う。したがって、

- `sessionId`自体を安全に解釈できないレコード（§4.2参照）、未知の`schemaVersion`を持つレコード、読込時に異常と判定されたレコード（§5-10）は、**軸Aの判定自体が不確実であるため、自動削除（prune）の対象に含めない**。
- 自動pruneは配列全体を計算し直して書き戻す処理である。**軸Aを安全に判定できないレコードが1件でも存在する場合、そのレコードを含むprune計算の結果が不正レコードを失わせる可能性があるときは、prune全体の実行自体を保留する**（その回のpruneは何も削除せずに終了し、次回、安全に軸Aを判定できる状態になった時点で再度試みる）。「安全に判定できないものは削除せず持ち越す」を一律の原則とする。
